# フレンズアクティビティ (FriendsActivity) 変更履歴・設計決定録 (ADR)

## 2026-05-31 初版作成

* **変更内容**: フレンズアクティビティ機能の設計書一式を作成。基本設計 (機能概要書・機能一覧・画面遷移図・ER図) および詳細設計 (UI設計書・ドメイン定義書・処理詳細/I-O定義書) の全7文書を整備した。
* **背景・理由 (Why)**: 既に実装が完了している友人視聴共有機能について、設計意図・データモデル・処理フロー・UI仕様を文書化し、今後の保守・機能拡張時の参照基盤とするため。
* **見送った代替案**:
  - コード内コメントのみで設計を管理する案: コード変更に追従しにくく、全体像の把握が困難になるため見送り。
  - 単一の設計書にまとめる案: 分量が多く参照性が低下するため、基本設計と詳細設計に分割した構成を採用。

### 主な設計決定

#### ADR-001: 友達ペアの正規化格納 (user_id < friend_user_id)

* **決定**: `sys_user_friends` テーブルにおいて `user_id < friend_user_id` の制約で1レコードのみ格納し、双方向の参照を実現する。
* **背景・理由**: 2レコード方式 (A→B, B→A) に比べてデータ量が半減し、ユニーク制約による重複防止が容易。検索時は `user_id = :uid OR friend_user_id = :uid` の条件と `CASE WHEN` で双方向に対応する。
* **見送った代替案**: 2レコード方式 (双方向レコード) -- クエリは単純化されるが、登録/削除時に2レコードの整合性管理が必要になるため不採用。

#### ADR-002: 友達とグループの統合閲覧可能ユーザー導出

* **決定**: 友達ペア (`sys_user_friends`) とグループメンバー (`sys_user_group_members`) を `FriendGroupModel::getViewableUserIds()` でマージし、重複排除した「閲覧可能ユーザーID一覧」を返却する。
* **背景・理由**: 2つの関係性定義方式 (1対1ペアとN対Nグループ) を統一的に扱うことで、視聴データ取得ロジックをシンプルに保つ。
* **見送った代替案**: 友達とグループで別々のAPI/画面を分ける案 -- ユーザー体験が分断されるため不採用。

#### ADR-003: 3ジャンル統合表示とsort_dateによるソート

* **決定**: アニメ・映画・ドラマの視聴済みデータをアプリケーション層で配列マージし、`sort_date` (`watched_date` or `updated_at`) の降順でソートして統合一覧を返却する。
* **背景・理由**: 各テーブルのスキーマが異なる (アニメは `annict_work_id` / 映画・ドラマは `tmdb_id` 等) ため、SQL UNION では型の統一が煩雑。PHP側でのマージにより、各ジャンルの返却構造を柔軟に保ちつつソートを実現する。
* **見送った代替案**: SQL UNION ALLで結合する案 -- カラム構造の差異が大きく、型変換・NULLハンドリングが複雑化するため不採用。

#### ADR-004: 登録済み判定の突合方式

* **決定**: ログインユーザー自身の視聴登録データを事前に一括取得し (アニメは `annict_work_id` 一覧、映画/ドラマは `tmdb_id` → ステータスのマップ)、各アイテムに対してインメモリで突合する。
* **背景・理由**: 表示アイテムごとにDBクエリを発行するN+1問題を回避し、パフォーマンスを確保する。
* **見送った代替案**: 各アイテム表示時に個別にDBクエリを発行する案 -- アイテム数が多い場合にクエリ数が爆発するため不採用。

#### ADR-005: 管理者専用の友達・グループ管理

* **決定**: 友達ペアの登録/削除およびグループの作成/編集/削除は管理者 (`Auth::requireAdmin()`) のみが実行可能とし、一般ユーザーには友達追加/グループ参加の機能を提供しない。
* **背景・理由**: 小規模な利用想定 (家族・知人間) であり、ユーザー自身による友達申請・承認フローのような複雑な機能は不要。管理者が一元管理することで実装をシンプルに保つ。
* **見送った代替案**: ユーザー間の友達申請/承認フロー -- 通知機構・申請管理画面の開発コストに見合わないため見送り。
