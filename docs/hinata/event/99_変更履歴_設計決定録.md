# イベント管理・セットリスト・ライブガイド (event) 変更履歴・設計決定録 (ADR)

## 2026-06-07 初版作成
* **変更内容**: ソースコードリーディングに基づき、event サブドメインの設計書一式（11〜23）を初版作成した。
* **背景・理由 (Why)**: 既存実装のドキュメント化。イベント管理・セットリスト・ライブガイドの3領域を1サブドメインとして統合的に設計書化した。
* **見送った代替案**: イベント・セットリスト・ライブガイドを個別のドキュメントセットに分離する案。テーブル間の結合が密であり、分離するとER図や処理フローの記述が重複するため、統合を採用した。

### ADR-001: 4ビューモード（カレンダー/タイムライン/ダッシュボード/マスタディテール）の並列提供
* **変更内容**: イベント一覧画面に4つの表示モードを並列提供する設計とした。
* **背景・理由 (Why)**: 利用シーンによって最適な表示形式が異なる（月単位の予定確認→カレンダー、時系列の振り返り→タイムライン、KPI把握→ダッシュボード、詳細編集→マスタディテール）。
* **見送った代替案**: 単一のリスト表示に統一する案。情報密度と操作性のバランスが取れないため見送り。

### ADR-002: hn_event_series による系列グルーピング
* **変更内容**: イベントの上位くくり（ツアー、単発ライブシリーズ等）を hn_event_series テーブルで管理する。
* **背景・理由 (Why)**: 同一ツアーの公演を横断的に管理（セットリスト共有、参戦実績の集計等）するため。
* **見送った代替案**: hn_events にタグカラムを持たせてグルーピングする案。リレーション情報（ツアー名、期間等）の管理に限界があるため見送り。

### ADR-003: hn_user_events_status によるユーザー別参加ステータス管理
* **変更内容**: イベントへの参加ステータス（参加予定/参加済み/不参加等）をユーザー×イベントの中間テーブルで管理する。
* **背景・理由 (Why)**: hn_events 本体にステータスを持たせると複数ユーザー対応ができない。座席情報・感想メモもユーザー単位で保持する必要がある。
* **見送った代替案**: hn_events にカラム追加する案。マルチユーザー対応が不可能なため見送り。

### ADR-004: セットリストの構造化保存（曲行 + MC/ブロック行 + 複数センター）
* **変更内容**: hn_setlists に楽曲行以外のメタ行（MC、アンコール区切り等）を track_type で区分して保存し、hn_setlist_centers でセンター情報を別テーブルに分離する。
* **背景・理由 (Why)**: 実際のライブセットリストにはMC・ブロック区切り・複数センター（Wセンター等）が存在し、単純な楽曲リストでは表現できない。
* **見送った代替案**: JSON カラムにセットリスト全体を格納する案。検索性・集計性が低下するため見送り。

### ADR-005: ライブガイドの楽曲確度（confidence）管理
* **変更内容**: hn_event_guide_songs に confidence カラムを設け、セットリスト入りの確度を段階管理する。
* **背景・理由 (Why)**: 初参戦者向けガイドでは「ほぼ確実に演奏される曲」と「演奏される可能性がある曲」を区別する必要がある。
* **見送った代替案**: 確度なしのフラットな楽曲リストとする案。優先度付きの予習ガイドを提供できないため見送り。

### ADR-006: 影ナレーション（shadow narration）の独立テーブル化
* **変更内容**: 影ナレ情報を hn_event_shadow_narrations + hn_event_shadow_narration_members で管理する。
* **背景・理由 (Why)**: 影ナレはイベント内の複数箇所（開演前・中間・終演後等）で発生し、各回に複数メンバーが担当する。hn_events のカラムでは表現できない。
* **見送った代替案**: hn_events に shadow_narration_text カラムを追加する案。複数回・複数メンバーの構造化ができないため見送り。
