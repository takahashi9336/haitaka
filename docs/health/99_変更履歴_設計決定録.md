# Health（ヘルスケア/健康管理） 変更履歴・設計決定録 (ADR)

## [2026-05-31] 初版作成

* **変更内容**: Health機能の設計書一式（基本設計2件＋詳細設計3件＋本ファイル）を新規作成した。対象は食材ストック・トレーニングメニュー・トレーニング実施履歴の3機能。
* **背景・理由 (Why)**: 既存の実装コード・マイグレーションSQLに対応する設計ドキュメントが存在しなかったため、現行実装を正とした逆設計（リバースドキュメンテーション）を行った。
* **見送った代替案**: 
  - テーブル定義を phpMyAdmin の SHOW CREATE TABLE から自動生成する案 → マイグレーションSQL群に十分な情報があり不要と判断。
  - 画面遷移図を flowchart LR で記述する案 → 各画面内のステート（フィルタ切替・インライン編集）を表現するため stateDiagram-v2 を採用した。

## [設計判断メモ] スナップショット保存方式

* **変更内容**: トレーニング実施履歴（`hl_training_logs`）では、HIIT記録時に `menu_snapshot`（JSON）カラムへ全種目のスナップショットを保存する設計とした。
* **背景・理由 (Why)**: メニューが後から編集・削除されても過去の実施記録の整合性を保つため。exercise 種別では `menu_name`/`reps`/`duration_sec` を個別カラムにスナップショット保存し、HIIT 種別では複数種目を JSON 配列で一括保存する。
* **見送った代替案**:
  - メニューの変更履歴テーブルを別途作成し、履歴から参照する案 → テーブル設計が複雑になる割に個人ユースでは過剰と判断。
  - 実施履歴からメニューマスタへの FK 参照のみで済ませる案 → メニュー削除時にデータが不完全になるため却下。現状は FK を SET NULL に設定し、スナップショットで補完している。

## [設計判断メモ] item_group のデータ型

* **変更内容**: `hl_kitchen_stock_items.item_group` は ENUM ではなく `varchar(32)` とした。
* **背景・理由 (Why)**: グループ種別の追加を ALTER TABLE なしで行えるようにするため。API側の `$allowedGroups` 配列で許可値を制御する。
* **見送った代替案**:
  - MySQL ENUM 型を使用する案 → 値の追加にスキーマ変更が必要で運用コストが高いと判断。
  - 別途マスタテーブル（`hl_kitchen_stock_groups`）を作成する案 → 現状3値で固定的であり、過剰な正規化と判断。
