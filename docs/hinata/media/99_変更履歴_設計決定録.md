# メディア管理 (media) 変更履歴・設計決定録 (ADR)

## 2026-06-07 初版作成
* **変更内容**: ソースコードリーディングに基づき、media サブドメインの設計書一式（11〜23）を初版作成した。
* **背景・理由 (Why)**: 既存実装のドキュメント化。メディア管理（YouTube/TikTok/ブログ等）とバッチジョブを1サブドメインとして統合的に設計書化した。
* **見送った代替案**: バッチジョブを別ドキュメントセットに分離する案。バッチの出力先テーブルはメディア管理画面と共通であり、分離すると二重管理になるため統合を採用した。

### ADR-001: com_media_assets + hn_media_metadata の2層構造
* **変更内容**: メディアアセットの基本情報（URL・タイトル・サムネイル等）を com_media_assets（共通テーブル）に、日向坂固有のメタデータ（カテゴリ・管理フラグ等）を hn_media_metadata に分離する。
* **背景・理由 (Why)**: com_media_assets は Dashboard の YouTube 集中視聴など Hinata 以外の機能からも参照される共通リソースであり、日向坂固有の属性を混在させるとテーブルの汎用性が損なわれる。
* **見送った代替案**: 全カラムを1テーブルに統合する案。他機能との共有が困難になるため見送り。

### ADR-002: 4つの登録導線の並存
* **変更内容**: YouTube チャンネル検索、URL 貼り付け（oEmbed）、CSV/TSV 一括インポート、外部クライアント連携（TikTok）の4方式を並存させる。
* **背景・理由 (Why)**: メディアの種類（YouTube/TikTok/Instagram）や登録規模（1件/数十件/数百件）によって最適な登録方法が異なるため。
* **見送った代替案**: URL 入力のみに統一する案。大量登録時の効率が著しく低下するため見送り。

### ADR-003: hn_media_categories によるカテゴリ管理
* **変更内容**: メディアのカテゴリ（MV、Trailer、ダンスプラクティス、バラエティ等）を hn_media_categories マスタテーブルで管理し、hn_media_metadata.category で参照する。
* **背景・理由 (Why)**: カテゴリは運用中に追加・名称変更される可能性があり、マスタテーブルで管理することで柔軟に対応できる。
* **見送った代替案**: ENUM 型またはハードコード定数で管理する案。カテゴリ追加時にマイグレーションやコード変更が必要になるため見送り。

### ADR-004: バッチジョブのファイルキャッシュ + TTL 方式
* **変更内容**: スクレイピング結果を `private/cache/` 配下の JSON ファイルにキャッシュし、TTL（Time To Live）で有効期限を管理する。
* **背景・理由 (Why)**: 外部サイトへのアクセス頻度を抑制しつつ、ポータル表示時のレスポンスを高速化するため。Redis 等のキャッシュサーバーはさくらのレンタルサーバ環境では利用できない。
* **見送った代替案**: リクエスト時に毎回スクレイピングする案。外部サイトへの負荷とレスポンス遅延のため見送り。

### ADR-005: メンバー名自動検出による hn_media_members 紐付け
* **変更内容**: 動画タイトル・説明文からメンバー名を正規表現で自動検出し、hn_media_members に紐付けを行う。
* **背景・理由 (Why)**: 数百件のメディアに対して手動でメンバー紐付けを行うのは非現実的。タイトルにメンバー名が含まれるケースが多いため、自動検出で大部分をカバーできる。
* **見送った代替案**: 全件手動紐付けのみとする案。運用コストが高すぎるため見送り。

### ADR-006: hn_media_hashtags による動的ハッシュタグ管理
* **変更内容**: メディアにハッシュタグを付与する仕組みを hn_media_hashtags テーブルで管理する。
* **背景・理由 (Why)**: メディアの横断的な分類（#ひなたフェス2026、#コール動画 等）をカテゴリとは別軸で提供するため。ハッシュタグはユーザーが自由に定義できる。
* **見送った代替案**: hn_media_metadata に JSON 配列で持たせる案。ハッシュタグ別の一覧取得・集計が困難なため見送り。

### ADR-007: hn_song_media_links による楽曲×メディア紐付け
* **変更内容**: 楽曲とメディアの紐付けを中間テーブル hn_song_media_links で管理する（music サブドメインとの共有テーブル）。
* **背景・理由 (Why)**: 1つの楽曲に複数のMV/ダンプラ/ライブ映像が存在し、1つのメディアに複数楽曲が含まれる（メドレー等）ケースがあるため、多対多のリレーションが必要。
* **見送った代替案**: hn_media_metadata に song_id FK を持たせる案。多対多を表現できないため見送り。
