### ADR-001: 推しレベル体系に 0/1/7/8/9 の飛び番を採用する

* **変更内容**: 推しレベルの値として `0=その他, 1=気になる, 7=3推し, 8=2推し, 9=最推し` という飛び番の整数値を採用した（`FavoriteModel` 定数で定義）。

* **背景・理由 (Why)**: 初期実装では `level=2` を「推し」として使用していたが、推しの多段階化（最推し/2推し/3推し/気になる）の際に、既存データとの互換性を保ちつつ拡張するため、上位レベルに7-9を割り当てた。`level=1`（気になる）は複数メンバー設定可、`level=7-9` はユーザーあたり各1名の排他制約とすることで、推しスロットの概念を自然に表現できる。中間の2-6は将来の拡張（推しランクの細分化等）に備えて予約。

* **見送った代替案**:
  - 連番 `1/2/3/4` で定義し、3=3推し/4=最推し とする案 → 旧データ（level=2=推し）との衝突が発生し、マイグレーションが複雑化するため見送り。
  - 文字列型（'top', 'second', 'third', 'interested'）で定義する案 → ソート・比較演算が煩雑になり、パフォーマンスに影響するため見送り。

### ADR-002: メンバー画像を hn_member_images テーブルで管理し、hn_members.image_url を後方互換として残す

* **変更内容**: メンバー画像を1メンバーあたり最大5枚管理する `hn_member_images` テーブルを新設した。`hn_members.image_url` カラムは削除せず後方互換として残し、先頭画像の参照用に `image_url = images[0]` として同期する。

* **背景・理由 (Why)**: 当初はメンバー1名につき1枚の画像しか登録できなかったが、メンバー管理の詳細編集で複数枚の画像スロットが必要になった。既存の `image_url` カラムを削除するとビュー側の修正範囲が広くなるため、`hn_member_images` の先頭画像を `image_url` にも反映する二重管理方式を採用した。

* **見送った代替案**:
  - `hn_members` に `image_url_2` ~ `image_url_5` カラムを追加する案 → テーブル定義が冗長になり、画像枚数の上限変更時にスキーマ変更が必要になるため見送り。
  - `hn_members.image_url` を即座に廃止する案 → View/API 側の影響範囲が大きく、段階的移行が必要なため見送り。将来的に全参照先が `hn_member_images` を使うようになった時点で廃止を検討する。

### ADR-003: 推しレベル設定APIを TalkController に配置する

* **変更内容**: 推しレベル設定API（`toggle_favorite.php`）のルーティング先を `TalkController::toggleFavorite()` とした。OshiController ではなく TalkController に配置されている。

* **背景・理由 (Why)**: 元々「お気に入りトグル」機能はミーグリネタ帳（TalkController）の一部として実装されていた。推し機能の独立化（OshiController 新設）後も、既存のフロントエンド呼び出しパスとの互換性を維持するため、API エントリポイントの移動を見送った。ビジネスロジック自体は `FavoriteModel::setLevel()` に集約されており、Controller はルーティングの役割のみ。

* **見送った代替案**:
  - OshiController に `toggleFavorite()` を移動し、API ファイルのルーティングも変更する案 → 画面側（推し設定画面、メンバー帳、メンバー個別ページ）の全ての呼び出し先を変更する必要があり、影響範囲が大きいため見送り。
  - 両方のControllerに同一メソッドを用意して段階的移行する案 → コードの重複が発生するため見送り。

### ADR-004: マイフォト画像のリサイズ処理をサーバーサイドで実施する

* **変更内容**: マイフォト（hn_oshi_images）およびユーザープロフィール画像のアップロード時に、`OshiImageModel::resizeImage()` でサーバーサイドリサイズを行う。長辺が1200pxを超える場合のみアスペクト比を維持して縮小し、JPEG品質85/PNG圧縮レベル6/WebP品質85で保存する。

* **背景・理由 (Why)**: ユーザーがスマートフォンの高解像度カメラ画像（4000px超）をそのままアップロードした場合、ストレージ容量とページ表示速度に悪影響を及ぼす。クライアントサイドリサイズはブラウザ互換性の問題があり、サーバーサイドでの統一的なリサイズが確実。

* **見送った代替案**:
  - クライアントサイド（Canvas API）でリサイズしてからアップロードする案 → Safari旧バージョンでの動作不安定、Exif回転の扱いの差異があるため見送り。
  - リサイズせずにオリジナル画像をそのまま保存する案 → ストレージ圧迫と表示速度低下のため見送り。
  - 外部画像処理サービス（Cloudinary等）を利用する案 → 個人プロジェクトのコストに見合わないため見送り。

### ADR-005: ペンライトカラー表からポカ（長濱ねる）を除外する

* **変更内容**: ペンライトカラー表（`PenlightController::index`）では、`MemberGroupHelper::POKA_MEMBER_ID` に該当するメンバーをフィルタ除外する。

* **背景・理由 (Why)**: ポカ（id=0、長濱ねる）は卒業済みかつ特殊な位置づけのメンバーであり、サイリウムカラーが運用上使用されないため、初心者向けのペンライトカラー表に掲載すると混乱を招く。メンバー帳やメンバー管理画面では引き続き表示する。

* **見送った代替案**:
  - `is_active=0` の卒業メンバーを全て除外する案 → 卒業メンバーのサイリウムカラーを確認したいユーザーもいるため、卒業切替トグルで対応し、ポカのみ個別除外とした。

### ADR-006: 推しタイムラインを UNION ALL で構築する

* **変更内容**: メンバー個別ページのタイムラインAPIを、ブログ・ニュース・スケジュール・イベント・動画の5テーブルを UNION ALL で結合し、`event_date DESC` でソートする方式で実装した。スケジュールとイベントは当日以前のもののみ表示する。

* **背景・理由 (Why)**: 異なるテーブルに分散するメンバー関連情報を時系列で統合表示するため。各テーブルの構造が異なるため、共通カラム（type, id, title, thumbnail_url, event_date, url, extra）にマッピングして UNION ALL する方式が最もシンプル。動画の追加メタ情報は `extra` カラムに `JSON_OBJECT()` で格納し、クライアント側でパースする。

* **見送った代替案**:
  - 各データソースを個別APIで取得し、フロントエンドでマージ・ソートする案 → API呼び出し回数が増加し、ソート処理の実装が複雑化するため見送り。
  - マテリアライズドビューやイベントテーブルに統合する案 → データ更新時の同期コストが高く、現在の規模では過剰設計のため見送り。

### ADR-007: hn_user_member_profiles をユーザー+メンバーで UNIQUE 制約とし UPSERT で管理する

* **変更内容**: ユーザー固有のメンバープロフィール画像テーブル `hn_user_member_profiles` に `UNIQUE KEY (user_id, member_id)` を設定し、画像更新時は `INSERT ... ON DUPLICATE KEY UPDATE` で UPSERT する。旧画像ファイルは物理削除する。

* **背景・理由 (Why)**: ユーザーが任意のメンバーに対して独自のプロフィール画像を1枚だけ設定できる仕様であり、1ユーザー1メンバーにつき1レコードの制約が自然にマッチする。UPSERT により INSERT/UPDATE の分岐ロジックが不要になり、コードがシンプルになる。

* **見送った代替案**:
  - 履歴テーブルとして複数レコードを保持し、最新を参照する案 → 画像の履歴管理の要件がなく、ストレージを無駄に消費するため見送り。
