### ADR-001: リリースと楽曲を親子関係（ON DELETE CASCADE）とする

* **変更内容**: `hn_songs.release_id` に ON DELETE CASCADE 制約を設け、リリース削除時に収録曲を連鎖削除する設計とした。さらに `hn_song_members` も `hn_songs.id` に対して CASCADE を設定し、楽曲削除時にメンバー情報も連鎖削除される。

* **背景・理由 (Why)**: リリースと楽曲は強い親子関係にあり、リリースなしに楽曲だけが存在するケースは運用上あり得ない。削除時の孤児レコード発生を防ぎ、管理画面からのリリース削除をワンアクションで完結させるため。

* **見送った代替案**:
  - 論理削除（`deleted_at` カラム）方式 → リリースと楽曲の両方に論理削除フラグを持たせる必要があり、クエリの WHERE 条件が煩雑化するため見送り。現時点では削除頻度が低く、物理削除で十分と判断。
  - ON DELETE SET NULL 方式 → 楽曲がリリースから切り離されて孤立するため、データ整合性が崩れる。見送り。

### ADR-002: 参加メンバー保存を全件洗い替え方式とする

* **変更内容**: `SongMemberModel::bulkInsertMembers()` は、トランザクション内で対象楽曲の既存メンバーを全件 DELETE した後に新規 INSERT する洗い替え方式を採用した。`ReleaseMemberImageModel::saveForRelease()` や `ReleaseEditionModel::saveForRelease()` も同じ洗い替え方式。

* **背景・理由 (Why)**: フォーメーション編集はメンバーの追加・削除・順序変更が同時に発生するため、差分更新（UPSERT）よりも全件洗い替えの方がロジックがシンプルかつバグの温床になりにくい。1楽曲あたりのメンバー数は最大でも20-30名程度であり、パフォーマンス上の問題はない。

* **見送った代替案**:
  - 差分更新（UPSERT / MERGE）方式 → 追加・変更・削除の3パターンを個別に検出する必要があり、ロジックが複雑化。特にフォーメーションの `position` 変更と `row_number` 変更が同時に起こるケースで差分計算が困難になるため見送り。
  - フロントエンドで差分を計算して送信する方式 → クライアント側の複雑性が増し、ネットワークエラー時の整合性担保が難しいため見送り。

### ADR-003: アーティスト写真に object-cover object-top を適用する

* **変更内容**: フォーメーション表示およびアーティスト写真一覧で、メンバー画像を `object-cover object-top` で表示する設計ルールを設けた。

* **背景・理由 (Why)**: アイドルのアーティスト写真は上半身（バストアップ）が多く、`object-cover` + デフォルトの `object-center` では頭部（髪の毛や頭頂部）が切れてしまうケースが頻発した。`object-top` を指定することで、画像の上端を基準にトリミングし、顔が確実に表示領域内に収まるようにした。

* **見送った代替案**:
  - `object-contain` で画像全体を表示する案 → 正方形コンテナ内に余白（レターボックス）が発生し、グリッド表示時の統一感が損なわれるため見送り。
  - `object-cover object-center`（デフォルト）→ 上述の通り頭部切れが頻発するため不採用。
  - フォーカスポイント（focal point）を画像ごとに登録する案 → 管理工数が膨大になるため見送り。`object-top` で大半のケースをカバーできると判断。

### ADR-004: 楽曲動画の紐付けを中間テーブル（hn_song_media_links）に移行する

* **変更内容**: 従来は `hn_songs.media_meta_id`（1楽曲に1動画）で動画を紐付けていたが、`hn_song_media_links` 中間テーブルを新設し、1楽曲に複数動画（MV、Call動画、ダンス動画等）を紐付けられるようにした。`hn_songs.media_meta_id` はレガシーカラムとして残置し、既存データは移行済み。

* **背景・理由 (Why)**: 1つの楽曲に対してMV、コール動画、ダンスプラクティス動画など複数の関連動画が存在するケースが一般的であり、1:1の制約では表現できない。中間テーブル方式により、動画のカテゴリ別表示（MV優先ソート）も `hn_media_metadata.category` を参照するだけで実現可能になった。

* **見送った代替案**:
  - `hn_songs` に `media_meta_id_2`, `media_meta_id_3` 等のカラムを追加する案 → 拡張性が低く、カラム追加のたびにスキーマ変更が必要になるため見送り。
  - JSON カラムに動画ID配列を格納する案 → 外部キー制約が効かず、動画側からの逆引きクエリが非効率になるため見送り。

### ADR-005: リリース版別情報を hn_release_editions として正規化する

* **変更内容**: リリースの版ごとのジャケット画像を `hn_releases` に直接持たず、`hn_release_editions` テーブルに分離した。UNIQUE KEY `(release_id, edition)` で同一版の重複を防止。

* **背景・理由 (Why)**: シングルリリースは TYPE-A ～ TYPE-D + 通常版の最大5版が存在し、各版でジャケット画像が異なる。`hn_releases` に `jacket_type_a_url`, `jacket_type_b_url`, ... と水平展開するとカラムが肥大化し、版数がリリースによって異なる（アルバムは1版のみ等）ため NULL カラムが多発する。正規化テーブルに分離することで柔軟性とクエリの簡潔さを両立した。

* **見送った代替案**:
  - `hn_releases` に版ごとの画像カラムを直接追加する案（`jacket_type_a_url` 等）→ 上述の通り、NULL 多発とカラム肥大化のため見送り。
  - JSON カラムに版別情報をまとめて格納する案 → リレーショナルな制約（UNIQUE, FK）が効かず、個別版の検索が非効率になるため見送り。

### ADR-006: フォーメーション表示条件を全メンバー position 非NULL とする

* **変更内容**: フォーメーション図は、楽曲の全参加メンバーの `position` が非NULL である場合のみ表示する。一人でも `position` が NULL のメンバーがいる場合はフォーメーション非表示とした。

* **背景・理由 (Why)**: `position` が未設定のメンバーがいる場合、フォーメーション図としての配置が不完全であり、視覚的に誤解を招く表示になる。中途半端なフォーメーション図を表示するよりも、完全にデータが揃うまで非表示にする方がユーザー体験として望ましいと判断した。

* **見送った代替案**:
  - `position` 未設定のメンバーを「フォーメーション外」として別エリアに表示する案 → フォーメーション編集中の途中状態と完成状態の区別がつかず、ユーザーが混乱するため見送り。
  - フォーメーション表示の ON/OFF フラグを楽曲レコードに持たせる案 → 管理者が手動でフラグを切り替える手間が増えるため見送り。`position` の入力状態から自動判定する現方式の方が運用負荷が低い。

### ADR-007: 画像アップロードAPIをジャケットとアー写で個別エンドポイントとする

* **変更内容**: ジャケット画像アップロード（`upload_release_jacket.php`）とアー写画像アップロード（`upload_release_artist_photo.php`）を独立した API エンドポイントとし、保存先ディレクトリ（`img/releases/` / `img/releases/artist/`）とファイル名プレフィクス（`jacket_` / `artist_`）を分離した。

* **背景・理由 (Why)**: 保存先を物理的に分離することで、画像の用途が明確になり、ディスク使用量の把握やバックアップ運用が容易になる。また、将来的に画像サイズ制限やリサイズ処理を用途ごとに変えたい場合にも対応しやすい。

* **見送った代替案**:
  - 汎用画像アップロード API（`upload_image.php?type=jacket|artist`）で統合する案 → `type` パラメータの検証ロジックが必要になり、保存パスの決定ロジックが複雑化するため見送り。

### ADR-008: 認可を二層構成（エントリ PHP + Controller）とする

* **変更内容**: API エンドポイント（`save_release.php`, `delete_release.php`, `detail_release.php`）ではエントリ PHP で `Auth::check()` + ロール確認（`$_SESSION['user']['role']`）を行い、Controller メソッド内でも `HinataAuth` による認可チェックを行う二層構成とした。一方、`save_song_members.php` や `save_release_member_images.php` ではエントリ PHP は Controller へのルーティングのみで、認可は Controller 内で完結する。

* **背景・理由 (Why)**: エントリ PHP での事前チェックにより、不正リクエストを Controller のインスタンス化前に遮断でき、無駄なオブジェクト生成を回避できる。ただし全 API で統一できていない（一部はエントリ PHP でのチェックを省略）のは、開発時期の違いによるもので、将来的にはミドルウェア層への統合を検討する。

* **見送った代替案**:
  - エントリ PHP のみで認可を行い、Controller では認可チェックしない案 → Controller が直接呼び出されるケース（テスト等）で認可が漏れるリスクがあるため見送り。
  - すべて Controller 内で完結させる案 → 上述のインスタンス化コストの問題があるが、統一性の観点からは今後の改善候補として残置。
