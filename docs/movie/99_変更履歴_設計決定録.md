# 映画（Movie） 変更履歴・設計決定録 (ADR)

## 2026-05-31 初版作成

* **変更内容**: `docs/movie/` に基本設計（機能概要書・機能一覧・画面遷移図・ER図）および詳細設計（UI設計書・ドメイン定義書・処理詳細/I-O定義書）・本 ADR を作成。実装は `private/apps/Movie/` / `www/movie/` を根拠とした。
* **背景・理由**: AI・開発者が同一リファレンスを共有し、映画機能の全体像と詳細仕様を一元的に参照可能にするため。
* **見送った代替案**: 全コントローラメソッドの入出力をパラメータレベルで逐一列挙する形式は、メンテコストが高いため一覧表＋代表フロー記述に留めた。

### 設計上の主要な決定事項

1. **TMDBキャッシュ＋ユーザーリストの2テーブル構成**: mv_movies を全ユーザー共有の映画マスタ（TMDB情報キャッシュ）とし、mv_user_movies でユーザーごとの状態（watchlist/watched・rating・memo・tags）を管理する分離設計を採用。
   - *不採用案*: ユーザーごとに映画情報を重複保持する1テーブル構成。データ重複と更新コストの観点から不採用。

2. **仮登録（tmdb_id = NULL）の許容**: TMDB検索でヒットしない映画もタイトルのみで登録可能にし、後から TMDB 紐付けできる設計。
   - *不採用案*: TMDB必須とする案。マイナー映画や未公開作品を登録できなくなるため不採用。

3. **ガチャのファイルベース状態管理**: `GachaState` による JSON ファイル管理（DB テーブルを持たない）。日次リセット・最大2回の制約をクライアント/サーバー双方で管理。
   - *不採用案*: DB テーブルでガチャ状態を管理する案。ガチャは軽量な補助機能であり、DB スキーマを増やすほどの永続性は不要と判断。

4. **レコメンドのファイルキャッシュ（6時間TTL）**: TMDB API のレート制限と応答速度を考慮し、レコメンド結果をファイルキャッシュ。ユーザー別（personal/genre）と全体共有（trending）の2パターン。
   - *不採用案*: DB キャッシュテーブル。キャッシュの有効期限管理がファイルの mtime で十分シンプルに実現できるため不採用。

5. **出演者情報の保存上限（cast 20 / director 10 / writer 10）**: ランキング集計に必要十分な人数に絞り、DB サイズとバッチ処理時間を抑制。
   - *不採用案*: 全 credits を保存する案。数百人規模になる作品もあり、ストレージ・処理コストが過大なため不採用。

6. **配信情報の JSON カラム保存**: `watch_providers` を構造化 JSON として mv_movies に保持。正規化テーブルを持たない。
   - *不採用案*: provider テーブルを別途作成し正規化する案。配信情報はキャッシュ目的で頻繁に変わるため、JSON カラムの方がメンテナンスが容易と判断。
