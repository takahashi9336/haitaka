### ADR-001: ポータルダッシュボードは読み取り専用集約とする

* **変更内容**: ポータルダッシュボード（`/hinata/index.php`）は各サブドメインのテーブルに対して参照（SELECT）のみを行い、書き込み操作は一切行わない方針とした。書き込みはポータル情報管理画面（`/hinata/portal_info_admin.php`）およびその配下APIに限定する。

* **背景・理由 (Why)**: ダッシュボードを読み取り専用にすることで、各サブドメイン（イベント・ミーグリ・リリース等）のデータ整合性をそれぞれのサブドメインが責務として管理できる。ポータル側の障害やバグが他サブドメインのデータを破壊するリスクを排除する。

* **見送った代替案**:
  - ポータルダッシュボードからも直接データ更新を可能にする案 → 責務の分離が曖昧になり、保守性が低下するため見送り。

### ADR-002: 推し切り替えをクライアントサイドJSON埋め込みで実現する

* **変更内容**: 推しメンバーの切り替え（最推し/2推し/3推し）をサーバーAPIへの再リクエストではなく、初回レンダリング時にPHP側で全推しデータをJSONとしてページに埋め込み、JavaScriptの`OshiPortal.switchMain(level)`でDOM更新する方式を採用した。

* **背景・理由 (Why)**: 推しは最大3名であり、データ量が小さい。API往復による遅延を排除し、オフラインに近い瞬間的な切り替え体験を実現するため。

* **見送った代替案**:
  - 推し切り替え時にAjax APIで都度データ取得する案 → 切り替えのたびにローディングが発生し、体感速度が劣化するため見送り。
  - LocalStorageに推しデータをキャッシュしてAPI呼び出しを減らす案 → キャッシュ無効化の制御が煩雑になるため見送り。

---

### ADR-003: 認証をHinataAuthラッパーに委譲する

* **変更内容**: Hinata固有の認証判定（`isHinataAdmin` / `requireHinataAdmin`）を`HinataAuth`クラスに集約し、`Core\Auth`をコンストラクタ注入で受け取る委譲パターンを採用した。ポータル情報管理やAPIでは`Auth::isHinataAdmin()`の直接呼び出しも許容する。

* **背景・理由 (Why)**: `Core\Auth`はアプリ横断の汎用認証基盤であり、Hinata固有のロール判定（`admin`または`hinata_admin`をHinata管理者とみなす）は専用クラスにカプセル化すべきと判断した。将来的にロール体系が変わった場合もHinataAuth内の変更で完結する。

* **見送った代替案**:
  - Controller内に直接ロール判定ロジックを記述する案 → 判定ロジックが分散し、ロール変更時の影響範囲が広がるため見送り。
  - `Core\Auth`にHinata固有メソッドを追加する案 → 汎用基盤にドメイン固有ロジックが混入するため見送り。ただし`Core\Auth::isHinataAdmin()`は利便性のため例外的に残置。

### ADR-004: ポータル所有テーブルを hn_topics / hn_announcements の2テーブル構成とする

* **変更内容**: ポータルが所有・管理するテーブルを`hn_topics`（トピック）と`hn_announcements`（お知らせ）の2テーブルに分離した。応募締め切り（`hn_event_applications`）はイベントテーブルとの外部キー関係があるため、ポータル情報管理画面からCRUD可能だがeventsサブドメインとの共有テーブルとして扱う。

* **背景・理由 (Why)**: トピックとお知らせはライフサイクルが異なる。トピックは日付範囲（`start_date` / `end_date`）で表示期間を制御し、お知らせは日時単位（`published_at` / `expires_at`）で制御する。スキーマレベルでこの違いを明示することで、クエリの最適化とインデックス設計を個別に行える。

* **見送った代替案**:
  - トピックとお知らせを1テーブル（`hn_portal_items`等）にまとめ、`item_type`カラムで区別する案 → カラム定義が冗長になり（日付型と日時型の共存）、インデックス効率が下がるため見送り。

---

### ADR-005: UI設計にガラスモーフィズムとメッシュグラデーション背景を採用する

* **変更内容**: ポータルダッシュボードのデザイン体系として、メッシュグラデーション背景（`mock-mesh`: 3つの放射グラデーションの重ね合わせ）とガラスモーフィズム（`mock-glass`: `backdrop-filter: blur(16px)` + 半透明白背景）を採用した。カードは`border-radius: 24px`で統一し、ホバー時に`translateY(-2px)`とシャドウ強化のインタラクションを付与した。

* **背景・理由 (Why)**: 日向坂46の明るくポップなグループイメージに合致する視覚表現を実現するため。また、`$themePrimaryHex`によるテーマカラー動的適用との親和性が高く、推しメンバーのカラーに合わせた画面全体のトーン変化を自然に表現できる。

* **見送った代替案**:
  - フラットデザイン（単色背景 + ボーダーなし）案 → 情報密度の高いダッシュボードではセクション境界が不明瞭になり、視認性が低下するため見送り。
  - カード影のみのマテリアルデザイン案 → テーマカラー変更時の背景との調和が取りにくいため見送り。

---

### ADR-006: カルーセル表示を2行グリッド横スクロール方式とする

* **変更内容**: YouTube・TikTokセクションのカルーセルを、従来の1行横スクロールではなく2行グリッド横スクロール方式（`yt-grid-scroll` / `tk-grid-scroll`）で表示する設計とした。矢印ボタン（`yt-arrow`）は端到達で自動非表示とする。

* **背景・理由 (Why)**: 1行表示では一度に表示できるカード数が少なく、大量の動画コンテンツを効率的に閲覧できない。2行グリッドにすることで表示面積あたりの情報密度を向上させつつ、横スクロールで全件アクセス可能とした。

* **見送った代替案**:
  - ページネーション方式（1ページN件ずつ表示）→ ページ送りの操作が重く、コンテンツの連続性が失われるため見送り。
  - 無限スクロール（縦方向）→ ポータル全体のスクロール量が過大になり、他セクションへのアクセス性が低下するため見送り。

### ADR-007: 画像アップロードAPIをトピック・お知らせで個別エンドポイントとする

* **変更内容**: 画像アップロードを`upload_topic_image.php`と`upload_announcement_image.php`の2つの独立APIとして実装し、保存先ディレクトリ（`img/topics/` / `img/announcements/`）とファイル名プレフィクス（`topic_` / `ann_`）を分離した。

* **背景・理由 (Why)**: 保存先を物理的に分離することで、画像の用途が明確になり、ディスク使用量の把握やバックアップ運用が容易になる。また、将来的に画像サイズ制限やリサイズ処理を種別ごとに変えたい場合にも対応しやすい。

* **見送った代替案**:
  - 汎用画像アップロードAPI（`upload_image.php?type=topic|announcement`）で統合する案 → エンドポイントは減るが、型パラメータの検証ロジックが必要になり、保存パスの決定ロジックが複雑化するため見送り。

---

### ADR-008: レスポンシブレイアウトにCSS Grid 10カラム方式を採用する

* **変更内容**: ポータルダッシュボードのPC表示（768px以上）に10カラムのCSS Gridレイアウト（`v2-grid`）を採用した。各セクションをグリッド行に配置し、推しエリア（全幅）、TOPICSと次のイベント（7:3分割）、リリースと誕生日（7:3分割）等の比率を定義した。SP（768px未満）では1カラム縦積みにフォールバックする。

* **背景・理由 (Why)**: 情報量の異なるセクション（メインコンテンツ vs サブ情報）を横並びにする際、12カラムでは分割粒度が細かすぎてクラス指定が煩雑になる。10カラムの7:3分割はポータルの主要レイアウトパターンに最適化されており、記述がシンプルになる。

* **見送った代替案**:
  - Flexboxのみで組む案 → 複数行・複数カラムの配置制御が複雑になり、行間のセクション高さ揃えが困難なため見送り。
  - 12カラムグリッド（Bootstrap互換）案 → 7:3分割が`col-8 col-4`近似となり、実際の視覚バランスに合わないため見送り。
